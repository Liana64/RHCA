### 4.4 Configure encrypted storage

#### 4.4.1 Encrypt and decrypt block devices, either physical or logical, using LUKS

**Create and mount a LUKS device**
```sh
cryptsetup [Tab]                          # Use tab completion
cryptsetup luksFormat /dev/device         # Create LUKS overlay
cryptsetup luksDump /dev/device           # Always backup your LUKS headers
cryptsetup open /dev/device name          # Open LUKS overlay and map device
mkfs.btrfs /dev/mapper/name               # Write filesystem to mapped device
mount /dev/mapper/name                    # Open mapped LUKS device
```

**Close and unmount a LUKS device**
```sh
umount /dev/mapper/name                   # Unmount LUKS device
cryptsetup close name                     # Close LUKS device
```

#### 4.4.2 Configure encrypted storage persistence using NBDE

Network-Bound Disk Encryption (NBDE) automates passphrase input so that servers can boot normally. See [Chapter 11](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/9/html/security_hardening/configuring-automated-unlocking-of-encrypted-volumes-using-policy-based-decryption_security-hardening) of the RHEL 9 Security Guide.

**Setup NBDE server**
```sh
dnf install -y tang                       # Install tang

semanage port -a -t tangd_port_t \        # Allow tangd server to use
-p tcp 7500                               # port 7500

firewall-cmd --add-port=7500/tcp \        # Permanently allow access to the
--permanent                               # port allocated for tangd

firewall-cmd --reload                     # Reload the firewall to apply changes

systemctl edit tangd.socket               # Update `[Socket]\nListenStream=80` to
\                                         # `[Socket]
\                                         # `ListenStream=`
\                                         # `ListenStream=7500`

systemctl daemon-reload                   # Reload

systemctl show tangd.socket -p Listen     # Show port used, if two ports show
\                                         # here then it means that you didn't
\                                         # add two `ListenStream` items

systemctl enable --now tangd.socket       # Enable tang
```

**Setup NBDE client**
```sh
dnf install -y clevis clevis-luks \       # Install clevis packages
clevis-dracut clevis-systemd

dnf install -y clevis-udisks2             # If your target device is USB storage
\                                         # this additional package is required

curl -f http://server/adv                 # Test tang server

clevis luks bind -f \                     # Bind tang server
-d /dev/device tang \
'{"url": "http://server"}'

clevis luks list                          # Show LUKS headers for all devices
clevis unlock -d /dev/device              # Test unlocking device
vim /etc/crypttab                         # Add headers to crypttab, being
\                                         # sure to use `_netdev` since we
\                                         # are using the network!

vim /etc/fstab                            # Add mapped device to fstab
findmnt --verify                          # Verify mount
dracut -f                                 # Rebuild initrd

systemctl enable remote-cryptsetup.target # This is required to correctly mount
\                                         # using clevis/tang at boot!
```

**Using NBDE for a root/swap volume**
```sh
echo "hostonly_cmdline=yes" > \           # Add `hostonly_cmdline=yes` to a
/etc/dracut.conf.d/clevis.conf            # dracut drop-in config file

dracut -fv --regenerate-all               # Regenerate initrd to require network
\                                         # for ramdisk initialization

dracut -fv --regenerate-all \             # If not using the drop-in file, you
--host-only-cmdline                       # can also do it this way, but the 
\                                         # drop-in file is more guaranteed to
\                                         # be persistent.

grubby --update-kernel=ALL \              # Alternatively, just update the
--args="rd.neednet=1"                     # kernel params directly

lsinitrd | grep clevis-luks               # Verify that bindings are available
```


**Example crypttab**
```crypttab
secure_drive UUID=<UUID from cryptsetup luksUUID device> none _netdev
```

If your device is mapped automatically, do not use the device mapper name for the LUKS volume as there may be a collision.

**Example fstab**
```fstab
/dev/mapper/secure_drive /mnt xfs _netdev 0 0
```

### 4.5 Restrict USB devices

See [Chapter 14](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/9/html/security_hardening/protecting-systems-against-intrusive-usb-devices_security-hardening) of the RHEL 9 Security Guide.

**Generate a usbguard policy**
```sh
semanage boolean -l | grep usbguard       # Enable booleans to allow the daemon
\                                         # to manage usbguard files

usbguard generate-policy \                # Generate policy based on current
> rules.conf                              # USB devices plugged in.

usbguard generate-policy --no-hashes      # Generate policy without any hashes

install -m 0600 -o root -g root \         # Install the rules.conf file with the
rules.conf /etc/usbguard/rules.conf       # correct permissions and ownership

stat /etc/usbguard/rules.conf             # Make sure rules.conf is set to 0600
\                                         # and owned by root:root

systemctl restart usbguard                # Restart usbguard to apply changes
usbguard list-rules                       # Validate that the rules exist

ausearch -m USER_DEVICE -ts recent        # Check for USBGuard auditd messages
```

#### 4.5.1 Install USBGuard

Install and generate a policy before enabling the service, otherwise you could be locked out of the system with no keyboard or mouse access.

**USBGuard basics**
```sh
dnf install -y usbguard                   # Install usbguard

usbguard generate-policy |                # Generate a policy with the current
>> /etc/usbguard/rules.conf               # devices **before** enabling service

chmod 0600 /etc/usbguard/rules.conf       # Must be perms 0600
chown root:root /etc/usbguard/rules.conf  # Must be owned by root user and group

systemctl enable --now usbguard           # Enable usbguard service
```

#### 4.5.2 Write device policy rules with specific criteria to manage devices

Rules are evaluated sequentially, so if a device is allowed and the same device is later blocked, it is still allowed.

**Listing and allowing devices**
```sh
usbguard list-devices                     # Show available devices
usbguard list-devices --blocked           # Show blocked devices
usbguard allow-device -p <device_id>      # Permanently allow a specific device
usbguard block-device -p <device_id>      # Permanently block a specific device
usbguard reject-device -p <device_id>     # Permanently reject a specific device

systemctl restart usbguard                # USBGuard must be restarted for rules
\                                         # to take effect.
```

See `man usbguard-rules.conf`

#### 4.5.3 Manage administrative policy and daemon configuration

Make sure to check each setting (e.g. `ImplicitPolicyTarget`) in the USBGuard daemon configuration so that you have no surprises. See `man usbguard-daemon.conf`

**Editing the USBGuard config**
```sh
vim /etc/usbguard/usbguard-daemon.conf    # Update USBGuard config, including
\                                         # specifying who can manage devices by
\                                         # editing `IPCAllowedUsers` and
\                                         # `IPCAllowedGroups`

systemctl restart usbguard                # Restart the USBGuard service

usbguard add-user -u <username> \         # Add a user with the ability to
--devices=list                            # list available devices.
```

### 4.7 Configure system auditing

Audit rules can monitor system calls and produce output in the auditd log. The `auditd` service is required for auditing to work.

**Auditd basics**
```sh
systemctl status auditd                   # Auditd service must be running
vim /etc/audit/auditd.conf                # Configure the auditd daemon *
vim /var/log/audit/audit.log              # View auditd log
```

Do not use `/etc/audit/audit.rules` as it is overwritten on restart.

**Understanding log components**

| Object       | Definition                                                                  |
| ------------ | --------------------------------------------------------------------------- |
| `1778704912` | Time, in epochs                                                             |
| `.370`       | Audit event ID, important for grouping multiple records                     |
| `arch`       | CPU architecture of system call, found using `uname -m` but generally `b64` |
| `msg`        | Auditd message                                                              |
| `scontext`   | Source context label                                                        |
| `tcontext`   | Target context label                                                        |
| `pid`        | Process PID                                                                 |
| `ppid`       | Parent process PID                                                          |
| `uid`        | User ID                                                                     |
| `auid`       | Audit UID, ID of the original user who caused the audit                     |
| `key`        | Filter key, used to easily find triggering records                          |
| `subj`       | SELinux label                                                               |
| `gid`        | Group ID                                                                    |
| `obj_uid`    | Object's UID                                                                |
| `obj_gid`    | Object's GID                                                                |
| `exe`        | Binary involved in audit record                                             |

See also `man auditctl`

**Example audit log**
```sh
type=CRED_REFR msg=audit(1778704912.370:219): pid=1794 uid=1000 auid=1000 ses=7 subj=unconfined_u:unconfined_r:unconfined_t:s0-s0:c0.c1023 msg='op=PAM:setcred grantors=pam_env,pam_faillock,pam_unix acct="root" exe="/usr/bin/sudo" hostname=lab-rhel9-n3 addr=? terminal=/dev/pts/0 res=success'
```

**Reading auditd timestamps**
```sh
date -d @<epoch_timestamp>                # Translate epoch timestamp
```

#### 4.7.1 Write rules to log auditable events

**Understanding auditd rules**

Two types of rules: watches or file system rules and system call rules.
- The first rule that matches is applied and then auditd exits skipping the rest.
- Specific rules win

**Updating auditd rules**
```sh
vim /etc/audit/rules.d/<some>.rules       # Auditd rules go here
augenrules --load                         # Reload auditd, on the exam just reboot
```

**Using auditctl**
```sh
auditctl -l                               # List auditd rules
auditctl -s                               # Show kernel subsystem status
auditctl -D <key>                         # Delete auditd rule by key
auditctl -w <file/path> \
-p <permissions> \
-k <key/value pair>

auditctl -a always,exit -F arch=b64 \     # Create an auditd rule to monitor
-F path=/sbin -F perm=x -k execute_bin    # binaries executed in /sbin on x64

auditctl -a always,exit -F arch=b32 \     # Create an auditd rule to monitor
-F path=/sbin -F perm=x -k execute_bin    # binaries executed in /sbin on x32

auditctl -a never,exit -F arch=b64 \      # Never audit a systemcall
-F path=/sbin -F perm=x

service auditd restart                    # The only way to restart auditd!
```

**Auditd related kernel parameters**
```sh
grubby --remove-args="audit=0" \          # Remove disabled auditd from
--update-kernel=ALL                       # kernel parameters
```

**Using ausearch and autrace**
```sh
ausearch -m AVC,USER_AVC -ts recent       # Show recent SELinux events

ausearch -m \
AVC,USER_AVC,SELINUX_ERR,USER_SELINUX_ERR # Show all SELinux-related events

ausearch -p <PID>                         # Show audit logs from PID
ausearch -k <KEY>                         # Show audit logs from key
autrace /bin/pwd                          # Trace all system calls using auditd
```

`ausearch` is more readable than viewing log files directly.

**Make auditd rules persistent**
```sh
auditctl -l >> \                          # Append loaded auditd rules to the
/etc/audit/rules.d/audit.rules            # persistent drop-in file
```

#### 4.7.2 Enable prepackaged rules

Remember that if you copy files from this folder and include `99-finalize.rules`, any rules that aren't placed with numbering, e.g., `35-custom.rules` will not take effect because of immutability.

**Using sample rules**
```sh

\                                         # to test (does not make persistent).
```

**Sample rules README file**
```sh
This group of rules are meant to be used with the augenrules program.
The augenrules program expects rules to be located in /etc/audit/rules.d/
The rules will get processed in a specific order based on their natural
sort order. To make things easier to use, the files in this directory are
organized into groups with the following meanings:

10 - Kernel and auditctl configuration
20 - Rules that could match general rules but we want a different match
30 - Main rules
40 - Optional rules
50 - Server Specific rules
70 - System local rules
90 - Finalize (immutable)

There is one set of rules, 31-privileged.rules, that should be regenerated.
There is a script in the comments of that file. You can uncomment the commands
and run the script and then rename the resulting file.

The rules are not meant to be used all at once. They are pieces of a policy
that should be thought out and individual files copied to /etc/audit/rules.d/
For example, if you wanted to set a system up in the STIG configuration, copy
rules 10-base-config, 30-stig, 31-privileged, and 99-finalize. You can add
more if you like. Also, not all arches have the same syscalls. It is expected
that the rules be fine tuned for the arch they are deployed on. For example,
aarch64 does not have the open syscall. It should just be deleted from the
rules.

Once you have the rules in the rules.d directory, you can load them by running
augenrules --load
```

### 4.8 Configure SELinux

SELinux is a Mandatory Access Control (MAC) security feature developed originally by Red Hat and the NSA. Works using kernel Linux Security Modules (LSM).

**Basic SELinux**
```sh
ls -lZ /tmp                               # List files including labels
ps fauxZ                                  # List processes including labels
ps -Z -C some_cmd                         # List context of a specific process
getenforce                                # Get current SELinux mode
setenforce [0/1]                          # Enable/disable SELinux enforcing
semanage fcontext -a -t label_t /path     # Label a path
restorecon -Rv /path                      # Recursively relabel path
getsebool -a                              # List all booleans (less confusing)
id -Z                                     # Get current user context
```

New files inherit the parent directory's label. Files that are moved are not considered new, so they retain their existing context information. See also `man semanage-fcontext`

**SELinux Documentation**
```sh
dnf install -y selinux-policy-doc
man -k selinux
```

#### 4.8.1 Enable SELinux on a host running a simple application

When working with applications be aware of application configuration, file system permissions, file context, and booleans.

#### 4.8.3 Restrict user activity with SELinux user mappings

There are SELinux users, roles, and types. SELinux users are different from linux users. The default SELinux user mapping is `__default__` which normally maps to `unconfined_u`. See also `man staff_selinux`.

When testing user mappings, remember to use ssh and `id -Z`, not `su`. `restorecon -Rv /home/<user>` may also be necessary (?).

**Managing users**
```sh
semanage user -l                           # List available SELinux users
semanage user -lC                          # List changed SELinux users

semanage login -l                          # List all SELinux user to linux user
\                                          # mappings.

semanage login -a -s user_u <user>         # Map SELinux user to linux user

semanage login -a -s sysadm_u <user>       # Make sure any administrative users
\                                          # have an SELinux user mapping before
\                                          # setting a default or you might get
\                                          # locked out and need to boot with
\                                          # `enforcing=0`! You can also use
\                                          # unconfined_u

setsebool -P ssh_sysadm_login 1            # Make sure a cloud-init user with
\                                          # the sysadm_u SELinux label and with
\                                          # SSH to root disabled can still
\                                          # connect and edit /root files
\                                          # without needing the unconfined_u
\                                          # role (?).

vim /etc/sudoers.d/user                    # Alternatively, create a sudoers
\                                          # mapping that grants sysadm_t access
\                                          # using `'cloud-user ALL=(ALL) TYPE=
\                                          # sysadm_t ROLE=sysadm_r ALL'` (?).

semanage login -m -s user_u -r s0 \        # Set default SELinux user mapping
__default__                                # to user_u for s0 MLS range, which 
\                                          # is the default range but in some
\                                          # cases is ncessary to specify.

id -Z                                      # Show SELinux user mapping for the
\                                          # current user.

useradd -Z staff_u <user>                  # Add a new user with user mapping

cat /etc/selinux/targeted/seusers          # Show SELinux user mappings using
\                                          # this file, which is readable by
\                                          # all users.
```

**Types of SELinux users**

| Label      | Description                | Man page         |
| ---------- | -------------------------- | ---------------- |
| `user_u`   | No `sudo` or `su`          | `user_selinux`   |
| `staff_u`  | No `su` but can use `sudo` | `staff_selinux`  |
| `sysadm_u` | Both `sudo` and `su`       | `sysadm_selinux` |

See also `semanage user -l`

#### 4.8.4 Analyze and correct existing SELinux configurations

If new files are created while SELinux is in permissive mode, they will not be labeled correctly. In this case, `fixfiles -F onboot` is required. Always switch to permissive mode (`enforcing=0`) from disabled mode (`selinux=0`) and investigate denials before enabling enforcing.

**Listing SELinux objects**
```sh
semanage fcontext -l                       # List available file context labels
semanage fcontext -lC                      # List changed file context labels
semanage boolean -l                        # List available booleans
semanage boolean -lC                       # List changed booleans
semanage port -l                           # List available ports
semanage port -lC                          # List changed ports
semanage module -l                         # List available modules
semanage module -lC                        # List changed modules
seinfo -r                                  # List available SELinux user roles
semanage user -l                           # List available SELinux users
semanage user -lC                          # List changed SELinux users
semanage login -l                          # List available SELinux user mappings
semanage login -lC                         # List changed SELinux user mappings
```

Note that if `setsebool` is used to change a boolean it will not show up when using `semanage boolean -lC` unless it is made persistent using `setsebool -P` or `semanage boolean -m <boolean> -1`

**Using audit2allow**
```sh
ausearch -m AVC,USER_AVC \                # Show module to allow an audit denial
-ts recent | audit2allow -m module

ausearch -m AVC,USER_AVC \                # Build module to allow an audit denial
-ts recent | audit2allow -M module        # STDOUT includes install instructions

cat module.te                             # Read module
semodule -i module.pp                     # Install module
```

**Disable SELinux state on boot**
```sh
grubby --args="selinux=0" \                # Disable SELinux entirely
--update-kernel=ALL

grubby --args="enforcing=0" \              # Disable enforcing (permissive mode)
--update-kernel=ALL

grubby --remove-args="selinux=0" \         # Remove param to disable SELinux
--update-kernel=ALL

grubby --remove-args="enforcing=0" \       # Remove param to disable enforcing
--update-kernel=ALL
```

If software doesn't support SELinux, it can also be configured to run in the `unconfined_t` domain. It's unsafe, but still less unsafe than disabling SELinux entirely. In some rare cases disabling SELinux entirely might be needed for a particular driver but is dangerous and not recommended.

**Using sepolicy**
```sh
sepolicy generate
```

**More on SELinux**
```sh
fixfiles -F onboot                        # Relabel all files on the system
touch /.autorelabel                       # Also relabels all files
reboot                                    # Reboot is required to trigger this

sestatus                                  # View status of SELinux, including
\                                         # the name of the loaded policy.
```

### 4.9 Enforce security compliance using OpenSCAP

Open Security Compliance Automation Protocol (OpenSCAP) is a tool used for auditing and enforcing security policies. Remediation packages can be generated for use with Ansible or Bash. The package `scap-security-guide` can also be used for security profile templates, e.g., "CIS Red Hat Enterprise Linux 10 Benchmark for Level 1 - Server"

Use OpenSCAP workbench wherever possible. Also, "ds" in the `ssg-rhel9-ds.xml` file stands for data stream.

#### 4.9.1 Install OpenSCAP and OpenSCAP Workbench

**Installing OpenSCAP**
```sh
dnf install -y openscap \                  # Install OpenSCAP
scap-workbench \                           # Install OpenSCAP Workbench (GUI)
scap-security-guide                        # Install security profiles
```

OpenSCAP must be installed on both client and target machines.

#### 4.9.2 Scan hosts for security compliance

**Using the OpenSCAP CLI**
```sh
ls /usr/share/xml/scap/sgg/content         # List XCCDF files

oscap info \                               # Show info on system, including
/usr/share/xml/scap/sgg/content/ \         # available profiles.
ssg-rhel9-ds.xml

oscap info --profile hipaa \               # Show info on HIPAA profile,
/usr/share/xml/scap/sgg/content/ \         # for example.
ssg-rhel9-ds.xml

oscap xccdf eval --profile \               # Evaluate a system XML file based
xccdf_org.ssgproject. \                    # on the selected profile ID and
content_profile_cis_server_l1              # save the results as an XML file.
--results /root/results.xml \              
/usr/share/xml/scap/sgg/content/ \
ssg-rhel9-ds.xml

oscap xccdf generate report \              # Convert results in an XML format
/root/results.xml > /root/results.html     # to a more readable HTML format.
```

#### 4.9.3 Tailor security policy

New, customized profiles can be "tailored" from existing security profiles.

**Using a tailoring file**
```sh
oscap xccdf eval --profile <custom_id> \   # Evaluate a system XML file based
--tailoring-file <tailoring_file.xml> \    # on a tailored (customized) profile
--results /root/results.xml \              # and save the results as an XML file.
--report /root/report.html \
/usr/share/xml/scap/sgg/content/ \
ssg-rhel9-ds.xml
```

#### 4.9.4 Scan individual hosts for security compliance

Create and save your customization file using OpenSCAP Workbench.

**Evaluating a target server using a tailoring file**
```sh
scp <custom.xml> <target>                  # Copy your customization file
oscap info <custom.xml>                    # Find ID for the profile
ssh <target> && sudo -i                    # Login to target and become root

oscap xccdf eval --profile <custom_id> \   # Evaluate a system XML file based
--tailoring-file /home/user/custom.xml \   # on a tailored (customized) profile)
--results /root/results.xml \              # and save the results as an XML file.
/usr/share/xml/scap/sgg/content/ \
ssg-rhel9-ds.xml
```

#### 4.9.5 Generate and apply a playbook from customized XML for remediation of inventory hosts

**Creating a remediation for a target server**
```sh
oscap info /root/results.xml | grep ID     # Get results-id

oscap xccdf generate fix --fix-type    \   # Generate an Ansible playbook from
ansible --result-id <result_id>        \   # a result-id,
--tailoring-file /home/user/custom.xml \   # using a tailoring file,
--output /root/remediate.yml           \   # output to a playbook,
/root/results.xml                          # from a results.xml file

ansible-playbook -K -i inventory \         # Run the playbook after adding
fix-playbook.yml                           # `become: true` to the header.
```
