# Red Hat Certified Engineer (EX294)

**Important**

- Carefully read the essential information and directions
- Never use ssh to remote hosts, always use Ansible
- Use `ansible-navigator -m stdout` to run playbooks
- Confirm that changes have been made and persist after reboot
- Always use idempotency
- Use FQCN for _ALL_ collection names
- Put `become: true` in your playbooks, _not_ in `ansible.cfg`
- Build out playbooks first with `- name:`, then `debug:` and conditionals, and finally with specific modules
- Use the provided documentation, as well as `ansible-doc` (options, return values, examples)
  - `ansible-doc -t keyword -l`, e.g., for `retries:` and `until:`
  - `ansible-doc -t filter -l`, e.g., for filters like `| checksum` or `| quote`
  - `ansible-doc regex_search -t filter`
- You have three breaks

**Remember**

- Setup Ansible
  - `ansible-config init --disabled > ansible.cfg`
    - `roles_path`, `collections_path`, `inventory`
- Setup `ansible-navigator`
  - `ansible-navigator settings --sample --pp missing > ansible-navigator.sample.yml`
  - Configure pull policy to be `missing`
- Use `$(date +%F)` in file names if needed
- Read roles documentation at `/usr/share/doc/rhel-system-roles`
- For SELinux, use the `rhel-system-role`
- When editing user groups, use `groups:`, not `group:` and `append: yes`!
- For the `inventory` you can make groups containing groups with `[groupname:children]`
- Use `ansible-galaxy role init` to create a role skeleton
- Custom facts are stored in `/etc/ansible/facts.d` on a managed host and must have a `.fact` extension and look like `[label] \n key=value`
  - Use `ansible all -m setup -a filter="ansible_local"` to show custom facts
- Blocks must have a `- name` header and can be paired with `rescue:` and `always:`
- `loop:` to access `{{ item.key }}`
  - You can also `loop:` directly into `- something \n - something else`
- `when:` can iterate multiple times, e.g., `- something \n - something else`
- You can `import_tasks:` or `import_role:` at the beginning of a playbook (static). Alternatively, use `ansible.builtin.include_tasks` or `ansible.builtin.include_role` on a when statement (dynamic, module)
- At the beginning of a playbook, you can `import_playbook`
- Use filters ` {{ somevar | int }}` or `{{ somevar | quote }}`
- Use `changed_when`, `failed_when`, and `fail:` to manage failures
- Use `handlers:` and `notify:` to access handlers
- Use `ansible.builtin.package_facts` to gather package facts, stored in `ansible_facts['packages']`
- Use templates with Jinja2
- The command module does not process shell characters, like pipe
- Use `pre_tasks:` and `post_tasks:` with `roles:`
- With roles, override variables in the `defaults` folder
- When defining variables, don't overwrite system variables, e.g., `groups`
- You can design a role and a playbook that calls `ansible.builtin.include_role`, and then makes sure there is a cron job task to run itself (the playbook calling the role)

**Examples**

- Use `regexp:` to replace lines in `ansible.builtin.lineinfile:`, including `?` to indicate that the `#` may or may not exist (changed), e.g.

```yaml
- name: replace line
  ansible.builtin.lineinfile:
    path: /etc/ssh/sshd_config
    regexp: "^#?PasswordAuthentication"
    line: "PasswordAuthentication no"
```

- Use the `find:` module and examples when needed (`ansible-doc find`):

```yaml
- name: Find files older than 4 weeks and equal or greater than 1 megabyte
  ansible.builtin.find:
    paths: /tmp
    age: 4w
    size: 1m
    recurse: yes
  register: old_backups
```

- Some features can iterate directly over a list:

```yaml
when:
  - some condition
  - some other condition
loop:
  - some thing
  - some other thing
```

- Example Jinja2

```jinja2
{% for item in sudo_groups %}
{% if item.sudo %}
{{ item.name }} ALL=(ALL) NOPASSWD:ALL
{% endif %}
{% endfor %}
```
